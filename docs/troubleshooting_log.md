# 문제 해결 기록

## 1. 넷리스트 주석의 중괄호가 템플릿을 깨뜨림
- **증상**: 첫 Python 실행에서 `KeyError: '중괄호'`.
- **원인**: 넷리스트를 `str.format`으로 채우는데, 주석에 "{중괄호} 자리"라고 쓴 게 자리표시로 해석됨.
- **해결**: 주석에서 중괄호를 빼고 "주석에 중괄호 금지"를 적어 둠.

## 2. 바이어스가 0인데 시뮬레이션은 "성공"
- **증상**: bias 1pA(사실상 꺼짐)인데 측정값이 전부 나옴: gain(10Hz) −2.8dB, UGF 7.3Hz, PM 93°. 실패해야 할 테스트가 통과 판정.
- **원인**: 회로는 꺼진 게 아니라 **아주 느린 증폭기**가 됐다. 대역폭은 bias 전류에 비례하고 저주파 이득은 거의 그대로다 (20µA: 22MHz, 1nA: 36.7dB / 2.3kHz, 1pA: 7Hz). 1pA에서는 0dB 교차(7Hz)가 gain을 재는 10Hz보다 아래로 내려가 "gain −2.8dB인데 UGF는 있음"이라는 앞뒤 안 맞는 측정이 됐다. 게다가 pA 전류는 누설 전류와 같은 크기라 동작점을 믿을 수 없다. ngspice는 오류 없이 끝나므로 "측정값 있음 = 성공"으로 보면 쓸 수 없는 회로를 정상 결과로 쓰게 된다.
  (처음엔 "누설 때문에 0dB 교차가 생긴다"고 잘못 설명했다. bias를 바꿔 가며 다시 보고 고침.)
- **해결**: UGF ≤ 10Hz 또는 gain ≤ 0dB면 "측정 무효: 증폭기로 동작하지 않음"으로 반환.
- **교훈**: exp-ops-agent의 critic 버그(20번)와 같은 종류. 도구가 "실행됨"과 "의미 있는 결과"를 구분해 주지 않으면 Agent와 최적화기가 쓰레기 값을 쫓는다. 최적화기는 이런 점을 오히려 "PM 93°, 좋음"으로 볼 수 있다.

## 3. 스펙은 멀쩡한데 tail 전류원이 선형 영역 (동작점 분석 도구로 발견)
- **증상**: 기본 사이징은 TT에서 gain 36.5dB, UGF 22MHz, PM 89.5°로 스펙상 문제없어 보였다. tail 노드는 0.17V.
- **동작점을 뽑아 보니**: tail 트랜지스터 |Vds| 0.169V < Vdsat 0.175V → 선형 영역(여유 −6mV). 증거 두 개: tail의 gds가 bias 미러의 **20배**(30µS vs 1.5µS, 저항처럼 동작), bias 20µA를 복사해야 하는데 **17.3µA**만 흘림. 15개 corner·온도 전부 건강하지 않음(최악 fs 125°C, −53mV).
- **고치는 방법 비교** (5 corner × 3 온도, 각 15회):

  | 변경 | 전 구간 건강 | 최악 여유 | gain | UGF |
  |---|---|---|---|---|
  | 기본 | 0/15 | −53mV | 35.6~37.1dB | 17~27MHz |
  | 입력 공통 전압 0.9 → 1.1V | **15/15** | +102mV | **30.1~35.4dB** | 19~28MHz |
  | tail W 4 → 16µm | 9/15 | +22mV | 35.6~37.0dB | 19~28MHz |
  | 입력쌍 W 4 → 16µm | 9/15 | +30mV | 35.0~36.8dB | 24~38MHz |

- **해석**: 한 가지 손잡이로는 깔끔하게 안 풀린다. 공통 전압을 올리면 전 구간 건강하지만 이득이 최대 6dB 떨어지고, 공통 전압은 보통 앞단 회로가 정하는 값이라 설계자가 마음대로 못 바꾼다. W를 키우면 이득은 지키지만 fs corner에서 여전히 경계. → 여러 손잡이를 같이 움직이고 corner로 확인해야 하는 문제, 즉 이 프로젝트의 Agent + 최적화기가 풀 문제다.
- **교훈**: exp-ops-agent의 "느린 정상 job"처럼, 스펙 숫자만 보는 평가는 이런 회로를 통과시킨다. 동작점 검사를 **채점과 검증 단계에 넣어야** 한다(LLM이 "괜찮아 보인다"고 넘어가지 못하게, 코드로).
