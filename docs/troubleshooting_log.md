# 문제 해결 기록

## 1. 넷리스트 주석의 중괄호가 템플릿을 깨뜨림
- **증상**: 첫 Python 실행에서 `KeyError: '중괄호'`.
- **원인**: 넷리스트를 `str.format`으로 채우는데, 주석에 "{중괄호} 자리"라고 쓴 게 자리표시로 해석됨.
- **해결**: 주석에서 중괄호를 빼고 "주석에 중괄호 금지"를 적어 둠.

## 2. 바이어스가 0인데 시뮬레이션은 "성공"
- **증상**: bias 1pA(사실상 꺼짐)인데 측정값이 전부 나옴: gain(10Hz) −2.8dB, UGF 7.3Hz, PM 93°. 실패해야 할 테스트가 통과 판정.
- **원인**: 회로는 꺼진 게 아니라 **아주 느린 증폭기**가 됐다. 대역폭은 bias 전류에 비례하고 저주파 이득은 거의 그대로다 (20µA: 22MHz, 1nA: 36.7dB / 2.3kHz, 1pA: 7Hz). 1pA에서는 0dB 교차(7Hz)가 gain을 재는 10Hz보다 아래로 내려가 "gain −2.8dB인데 UGF는 있음"이라는 앞뒤 안 맞는 측정이 됐다. 게다가 pA 전류는 누설 전류와 같은 크기라 동작점을 믿을 수 없다. ngspice는 오류 없이 끝나므로 "측정값 있음 = 성공"으로 보면 쓸 수 없는 회로를 정상 결과로 쓰게 된다.
  (처음엔 "누설 때문에 0dB 교차가 생긴다"고 잘못 설명했다. bias를 바꿔 가며 다시 보고 고침.)
- **해결**: UGF ≤ 10Hz 또는 gain ≤ 0dB면 "측정 무효: 증폭기로 동작하지 않음"으로 반환.
- **교훈**: exp-ops-agent의 critic 버그(20번)와 같은 종류. 도구가 "실행됨"과 "의미 있는 결과"를 구분해 주지 않으면 Agent와 최적화기가 쓰레기 값을 쫓는다. 최적화기는 이런 점을 오히려 "PM 93°, 좋음"으로 볼 수 있다.

## 3. 스펙은 멀쩡한데 tail 전류원이 선형 영역 (동작점 분석 도구로 발견)
- **증상**: 기본 사이징은 TT에서 gain 36.5dB, UGF 22MHz, PM 89.5°로 스펙상 문제없어 보였다. tail 노드는 0.17V.
- **동작점을 뽑아 보니**: tail 트랜지스터 |Vds| 0.169V < Vdsat 0.175V → 선형 영역(여유 −6mV). 증거 두 개: tail의 gds가 bias 미러의 **20배**(30µS vs 1.5µS, 저항처럼 동작), bias 20µA를 복사해야 하는데 **17.3µA**만 흘림. 15개 corner·온도 전부 건강하지 않음(최악 fs 125°C, −53mV).
- **고치는 방법 비교** (5 corner × 3 온도, 각 15회):

  | 변경 | 전 구간 건강 | 최악 여유 | gain | UGF |
  |---|---|---|---|---|
  | 기본 | 0/15 | −53mV | 35.6~37.1dB | 17~27MHz |
  | 입력 공통 전압 0.9 → 1.1V | **15/15** | +102mV | **30.1~35.4dB** | 19~28MHz |
  | tail W 4 → 16µm | 9/15 | +22mV | 35.6~37.0dB | 19~28MHz |
  | 입력쌍 W 4 → 16µm | 9/15 | +30mV | 35.0~36.8dB | 24~38MHz |

- **해석**: 한 가지 손잡이로는 깔끔하게 안 풀린다. 공통 전압을 올리면 전 구간 건강하지만 이득이 최대 6dB 떨어지고, 공통 전압은 보통 앞단 회로가 정하는 값이라 설계자가 마음대로 못 바꾼다. W를 키우면 이득은 지키지만 fs corner에서 여전히 경계. → 여러 손잡이를 같이 움직이고 corner로 확인해야 하는 문제, 즉 이 프로젝트의 Agent + 최적화기가 풀 문제다.
- **교훈**: exp-ops-agent의 "느린 정상 job"처럼, 스펙 숫자만 보는 평가는 이런 회로를 통과시킨다. 동작점 검사를 **채점과 검증 단계에 넣어야** 한다(LLM이 "괜찮아 보인다"고 넘어가지 못하게, 코드로).

## 4. 시뮬레이션 1회 12초 → 0.05초 (그리고 그 과정에서 멈춘 세션)
- **측정**: 전체 실행 10.9초, 모델 로딩 + op만 11.0초, 한 번 로딩 후 5번 계산 11.25초 → 실제 계산은 1회 약 0.05초, 나머지는 SKY130 모델 로딩.
- **해결**: (corner, 온도)마다 ngspice를 pipe 모드로 띄워 두고 `alterparam` + `reset`으로 파라미터만 바꿔 다시 계산. 15개 조건 전체 평가가 180초 → **0.16초** (첫 로딩 18초는 한 번만).
- **막힌 것 1 — 온도**: 세션 안에서 `option temp`가 무시됐다(.temp 줄을 지워도). → 온도도 세션 단위로. 세션 15개 × 350MB.
- **막힌 것 2 — 세션이 영원히 멈춤**: 파라미터 이름을 `ln`(입력쌍 L)으로 지었는데 ngspice 수식에서 `ln`은 **자연로그 함수**. 넷리스트 오류가 나자 ngspice가 "Run Spice anyway? y/n ?"를 묻고, 다음 명령 줄을 답으로 먹으며 무한 반복 → 응답을 기다리던 Python도 멈춤. 처음엔 batch 모드라 이 질문 없이 지나갔다.
  - 이름을 `l_in` 등으로 바꾸고, 출력에 `y/n ?`가 보이면 세션을 죽이고 오류로 반환.
- **함정 방지**: 세션은 상태가 남는다. 매 요청마다 모든 파라미터를 다시 설정하고 `destroy all`로 이전 결과 벡터를 지운다(측정 실패가 옛 값으로 가려지지 않게). 테스트: 다른 값으로 돌린 뒤 기본값이 batch 결과(36.533dB)와 정확히 같은지.

## 5. 스펙 정의와 Random Search 베이스라인: 스펙이 생각보다 쉬웠다
- **스펙**: gain ≥ 40dB, UGF ≥ 20MHz, PM ≥ 60°, 전력 ≤ 100µW, 모든 트랜지스터 포화 여유 ≥ 50mV, **15개 조건 전부**. 손잡이 7개(bias 전류, W/L 3쌍), 입력 공통 전압·부하 C는 고정.
- **Random Search** (TT 27°C로 거르고 통과하면 15개 조건 검증): **10/10 해결, 해결까지 시뮬레이션 중앙값 295회** (88 ~ 1370).
- **해석**: 시뮬레이션이 0.05초라 295회는 15초다. 이 회로·스펙에서는 무작위로도 금방 풀린다 → Agent가 이길 여지가 작다. 
  - Agent 비교가 의미 있으려면: (a) 스펙을 조여 무작위로는 잘 안 풀리게, (b) 시뮬레이션 1회가 비싼 상황(실제 업무의 post-layout, transient, 큰 회로는 분~시간)을 가정해 **시뮬레이션 횟수**를 주 지표로.
  - 해답들의 공통점(ibias 18~27µA, l_in 0.8~3.9µm로 기본 0.5보다 김, w_load 큼)은 규칙 기반 베이스라인과 Agent가 활용할 "설계 지식"이 실제로 있다는 신호.

## 6. 스펙 조이기: 감이 아니라 데이터로
- **방법**: 무작위 설계 3000개를 15개 조건 전부에서 한 번 시뮬레이션해 두고(`eval/sample_space.py`), 스펙 후보마다 통과 비율을 시뮬레이션 없이 계산.
  - 기존 40dB / 100µW: 11/3000 (0.37%). 42dB / 70µW: **2/3000 (0.07%)**. 그보다 조이면 0/3000 → 해가 있는지 알 수 없으니 고르지 않았다(해가 없는 문제를 Agent에게 주면 실패의 의미가 없다). 통과한 설계 하나로 "해가 있다"를 테스트로 고정.
- **새 스펙 Random Search** (2000회 예산, seed 10개): **해결 2/10** (494회, 1497회). 기존 스펙은 10/10, 중앙값 295회.
- **실패한 8개 seed 전부 TT 27°C는 통과한 후보를 찾았다** (최고 TT 점수 0). 떨어진 곳은 corner·온도 검증. → 이 문제의 어려움은 "TT에서 맞추기"가 아니라 "**모든 corner에서 버티기**"다. 실패 원인(어느 corner에서 무엇이 부족한가)을 읽고 고치는 것이 Agent가 기여할 수 있는 지점.
- **실수 두 개**: (1) 바깥 timeout을 1700초로 잡아 seed 4개 만에 잘림 → seed마다 프로세스를 따로 띄워 병렬로. (2) 끝났는지 기다리는 `while pgrep -f random_search` 루프가 **자기 자신의 명령줄**에 그 문자열이 있어 영원히 안 끝남. 같은 이유로 `pkill -f`가 내 셸을 죽인 것도 두 번. → 프로세스를 이름 패턴으로 찾지 말고 PID로 관리.

## 7. 규칙 기반 베이스라인: 기본값에서는 잘 풀고, 무작위 시작점에서는 막힌다
- **규칙**: 최악 조건에서 가장 급한 문제 하나에 교과서 규칙 하나(포화 여유 부족 → 그 소자 W↑, 전력 초과 → 전류↓, gain 부족 → L·W 같이↑, UGF 부족 → 전류↑ 또는 입력쌍 W↑, PM 부족 → 부하 L↓). 8번 연속 개선이 없으면 중단.
- **결과** (2000회 예산): 기본값 시작 **해결, 300회**(규칙 19번). 무작위 시작 10개 중 **해결 2개**(60회, 150회), 막힘 6개, 측정 실패 2개.
- **찾은 버그 — 내 규칙**: "UGF 부족(ff −40°C) → 전류↑"와 "전력 초과(fs 125°C) → 전류↓"가 번갈아 나옴. 전력 여유를 **최악 조건 한 곳**에서만 봤기 때문. 모든 조건의 최대 전력으로 바꿈(테스트 고정). 고친 뒤에도 해결 수는 같았다 → 막힌 진짜 원인은 따로 있음.
- **막힌 6개 전부: 규칙이 미는 손잡이가 범위 끝에 붙어 있었다** (입력쌍 W = 50µm 등). 같은 규칙이 효과 없이 반복. 그중 4개는 입력쌍 오버드라이브가 −5~34mV(약반전) → 거기서는 gm이 W가 아니라 전류로만 정해져서, 범위가 없었어도 W↑는 UGF를 못 올린다.
- **측정 실패 2개**: sf corner에서 이득이 한 번도 0dB를 넘지 않아 UGF를 잴 수 없음(증폭기로 동작 안 함). 이런 상태에 대한 규칙이 없다.
- **해석**: 규칙은 "이 증상엔 이 손잡이"가 고정이라, 손잡이가 한계에 닿거나 동작 영역이 바뀌어 규칙의 전제가 깨지면 전략을 못 바꾼다. 설계자라면 "W가 끝까지 갔고 약반전이니 L을 줄여 gm을 얻고 gain 여유와 맞바꾸자" 같은 판단을 한다 → Agent가 기여할 수 있는 지점이 구체적으로 보였다.

## 8. Agent 1차 평가: 무작위 시작점에서 규칙보다 훨씬 자주 풀었다 — 실패는 "단계 한도"
- **구성**: 도구 4개(15조건 채점, 한 조건 동작점, 손잡이 sweep, local_search 최적화기). 범위·예산·통과 판정은 코드. 채점이 통과하면 그 자리에서 종료. gpt-5-mini, LLM 호출 최대 40번, 시뮬레이션 예산 2000.
- **결과** (규칙 기반과 같은 시작점 11개, 시작점마다 1회):

  | 방법 | 기본값 시작 | 무작위 시작 10개 | 해결한 경우 시뮬레이션 |
  |---|---|---|---|
  | Random Search (seed 10개) | - | 2/10 | 494, 1497 |
  | 규칙 기반 | 해결 (300) | 2/10 | 60, 150 |
  | **Agent** | **실패** | **8/10** | 64 ~ 1050 (중앙값 약 210) |

  - 짝 비교(같은 시작점): Agent만 해결 6개(규칙이 범위 끝에 막혔거나 측정 실패로 손 못 댄 것 포함), 규칙만 해결 1개(기본값), 둘 다 2개, 둘 다 실패 2개.
  - 비용: Agent 11회 합계 약 $1.3, 실행당 $0.015~0.24, 1~10분.
- **실패 3개 모두 LLM 단계 한도(40번)에서 끝났다. 시뮬레이션 예산은 남아 있었다** (333~1351회 사용).
  - 기본값: 점수 0.0016까지 왔다(거의 통과). local_search를 6번 불렀지만 마지막 한 걸음을 못 넘음.
  - 무작위 0, 3: 진단 없이 evaluate_design을 연달아 부르며 **손으로 숫자를 바꿨고**, 회로를 망가뜨려(측정 실패, 점수 없음) 그 상태로 계속 평가. 프롬프트의 "진단 없이 숫자를 바꾸지 마라"를 지키지 않은 것 → exp-ops 15번과 같은 교훈: 반복되면 코드로 강제해야 한다.
- **같은 시작점도 결과가 다르다**: 기본값은 스모크 테스트에서 121회로 해결, 평가에서는 실패. 시작점마다 1회로는 Agent 해결률의 오차가 크다 → 반복 실행 필요.
- **평가 중 크래시**: 무작위 6에서 OpenAI가 프롬프트를 "사용 정책 위반 가능성"으로 거부(400) → 프로세스가 죽어 결과 누락. API 오류를 그 실행의 실패로 기록하게 고치고(테스트 고정) 다시 돌림 → 해결(179회).

## 9. "진단 없이 숫자 바꾸기"를 코드로 막았더니 — 효과 없음. 진짜 병목은 마지막 한 걸음
- **guard**: 직전 evaluate_design이 실패했는데 다른 도구 없이 다시 evaluate_design을 부르면 거부(시뮬레이션은 안 씀, 이유를 돌려줌). 8번의 실패 2개에서 본 패턴을 막으려고.
- **평가**: 같은 시작점 11개 × 3회, guard 끔/켬 (끔의 1회는 8번 결과). 66회, 약 $7.
  | | 해결 | 해결 시 시뮬레이션 중앙값 | LLM 호출 중앙값 | 비용 합 |
  |---|---|---|---|---|
  | guard 끔 | **24/33** | 183 | 24 | $3.67 |
  | guard 켬 | **23/33** | 147 | 22 | $3.28 |
  - 시작점별 해결률 차이(켬 − 끔) 평균 **−0.03, 95% CI [−0.15, +0.09]** → 효과를 주장할 수 없다. 거부는 37번 일어났다(그만큼 LLM 단계를 썼다).
- **실패를 다시 보니**: 19개 실패 중 18개가 LLM 단계 한도, 그리고 대부분 **거의 통과**였다 — 최고 점수가 0.05% ~ 2% 부족(끔 9개 중 7개, 켬 10개 중 7개가 2% 이내). 8번에서 본 "회로를 망가뜨리고 헤맴"은 반복해 보니 드물었다. **1회 결과에서 본 실패 패턴을 일반화했던 것**.
- **교훈**: (1) 고치기 전에 실패 원인을 충분한 표본으로 확인한다 — 1회짜리 실패 2개를 보고 guard를 만들었다. (2) 이 Agent의 병목은 진단이 아니라 **마지막 미세 조정**이다. 거의 다 온 상태에서 LLM이 손으로 숫자를 만지며 단계를 다 쓴다.
- **같은 조건 반복의 효과**: 8번에서 "기본값 실패"였던 시작점은 3회 중 2회 해결. Agent 해결률은 시작점 1회로 보면 크게 흔들린다.
- guard는 기본값으로 켠 채 두되(해롭지도 않음), 효과 없음을 기록. ablation용 옵션(`guard=False`)으로 남긴다.

## 10. 거의 통과하면 최적화기로 넘기기: 효과가 신뢰구간 밖으로 나왔다
- **먼저 오프라인으로 확인** (API 비용 없이): 9번 실패 19개에서 가장 좋았던 설계를 뽑아 최적화기로 마무리해 봄.
  - 실패한 조건만 채점: 6/19. 실패 조건을 고치다 다른 조건을 망가뜨려 바로 멈춘 경우가 있었다.
  - **15개 조건 전부 채점: 7/19, 그중 점수 1% 이내는 8개 중 7개.** 1%를 넘으면 대부분 예산(1000회) 안에 못 끝냄.
  → 기준을 "전체 점수 ≤ 0.01이면 넘김"으로, 방법은 기존 local_search(15조건, step 0.05)로. 새로 짠 마무리 함수는 지움.
- **구현**: 도구 결과의 전체 점수가 1% 이내면, LLM 판단을 기다리지 않고 코드가 local_search를 남은 예산으로 돌린다. 통과하면 끝, 실패하면 결과를 LLM에게 알려 주고 계속(더 좋아졌을 때만 다시 넘김).
- **평가** (guard 켬, 같은 시작점 11개 × 3회, 넘김만 다름. 약 $2.4):
  | | 해결 | 해결 시 시뮬레이션 중앙값 | LLM 호출 중앙값 | 비용 합 |
  |---|---|---|---|---|
  | 넘김 없음 | 23/33 | 147 | 22 | $3.28 |
  | **넘김** | **29/33** | 278 | **16** | **$2.44** |
  - 시작점별 해결률 차이 **+0.18, 95% CI [+0.06, +0.30]** → 0을 포함하지 않는다. 나빠진 시작점 없음.
  - 넘김은 20개 실행에서 일어났고 그중 19개가 넘김으로 해결. **남은 실패 4개는 1% 안으로 한 번도 못 들어왔다**(넘김 0회) → 이제 병목은 "가까이 가는 단계".
- **맞바꿈**: LLM 호출·비용은 줄고(−27%, −26%) 시뮬레이션은 늘었다(중앙값 147 → 278). 최적화기가 시뮬레이션을 많이 쓴다. 실무처럼 시뮬레이션 1회가 비싸면 이 맞바꿈이 불리할 수 있다 → 보고할 때 같이 말한다.
- **한계 (중요)**: 기준 1%는 **이 시작점들의 실패에서 정했다**. 같은 시작점으로 평가했으니 dev 점수다. 처음 보는 시작점(held-out)에서 확인해야 한다.
- **교훈**: 9번은 1회짜리 실패를 보고 고쳐서 효과가 없었고, 10번은 실패 19개를 먼저 분류하고 오프라인으로 고칠 수 있는지 확인한 뒤 고쳤다. 같은 Agent, 같은 평가 방식에서 차이는 **고치기 전에 원인을 확인했느냐**였다. LLM은 방향, 최적화기는 마지막 숫자 — 처음 계획한 역할 분담을 코드로 강제한 것.
